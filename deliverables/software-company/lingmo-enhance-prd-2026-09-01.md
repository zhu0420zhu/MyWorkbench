# 灵墨工作台 · 增量 PRD（2026-09-01）

> 本文档只描述**本轮增量变更**，不重复产品全貌。撰写前已核实代码现状（Analytics.tsx / DataLab.tsx / tablesCore.ts / stickyPanel.ts / StickyPanelWindow.tsx / stickies.ts / parseWorker·parseClient / main/index.ts）。
> 优先级：P0 必做 / P1 增强 / P2 可选。

---

## 一、产品目标

1. **分析更有价值**：数据分析从「画一张图」升级为「输出一组统计结论 + 可导出的分析报告」，让用户拿到数据即可获得可引用的结果。
2. **导入更快、体感更顺**：数据整理导入消除冗余往返与整表重复传输，导入期间界面保持可响应，大数据量有明确进度反馈。
3. **跨模块引用不卡**：数据分析引用数据整理表时，不再整表跨进程搬运，大表（数万～数十万行）下选择与切换均秒级响应。
4. **便利贴即点即用**：点击悬浮便利贴流畅展开为大尺寸便利贴，展开后可直接打开关联程序，整体交互闭环顺畅。

## 二、用户故事与验收标准

### 需求 1：分析深度增强 + 结果导出

**用户故事**
- 作为数据分析用户，我载入一份数据后，希望系统自动给出统计摘要（各数值列的最小/最大/均值/中位数/标准差/缺失值率）与关键结论（Top 类目、极值、整体趋势方向），无需自己盯着图猜。
- 作为数据分析用户，我希望对数值列查看分布（分箱直方图），发现长尾与集中区间。
- 作为数据分析用户，我希望把分析结果一键导出：图表存为 PNG、聚合明细与分析报告导出为 Markdown/HTML 文件，方便归档或分享。

**验收标准（Must）**
- [AC1.1] 选择 X/Y 列与聚合方式后，页面出现「分析结论」区域，自动列出：总行数、参与聚合行数、Top-N 类目及其占比、最大/最小值所在类目；纯文本结论，无空话。
- [AC1.2] 数值列提供分布直方图视图（分箱数 5～20 可调），与现有折线/柱状/饼图并列。
- [AC1.3] 提供「导出分析」：至少支持 ① 图表 PNG（echarts getDataURL）② 聚合结果 CSV ③ 完整分析报告 Markdown（含统计摘要表 + 结论文字 + 聚合明细表）。导出走现有 `exportText`/`exportBuffer` 通道。
- [AC1.4] 统计计算在现有数据规模上限（≤ 20 万行）下 < 500ms，不冻结主线程（必要时复用 Worker 模式）。

### 需求 2：数据整理导入提速

**用户故事**
- 作为数据整理用户，我导入一个几十 MB 的 CSV/Excel，希望进度可感知、界面不假死，导入完成后直接可编辑，全程比现在明显更快。

**验收标准（Must）**
- [AC2.1] 消除「create 空表 → update 整表」的双次写盘往返：新增/改造为一次导入 IPC，主进程收到解析结果后单事务落库（SQLite 200 行/批多值 INSERT 已就绪，直接复用）。
- [AC2.2] 导入 ≥ 10 万行 CSV 的端到端耗时相对现状可测量地下降（目标 ≥ 30%），且导入期间主窗口不出现可感知卡顿（解析已 Worker 化，需保持）。
- [AC2.3] 导入中有进度反馈（至少为解析完成/写入中两阶段的确定性提示），完成/失败均有消息，失败不产生半张脏表。
- [AC2.4] 导入完成后不把整表塞入前端状态再全量渲染：沿用「列表摘要 + 按需加载」模式。

### 需求 3：数据分析跨模块读取提速

**用户故事**
- 作为数据分析用户，我在分析页选择一张几十万行的数据整理表，希望下拉选中后 1 秒内看到可用结果，切换另一张表同样流畅。

**验收标准（Must）**
- [AC3.1] 新增主进程侧聚合查询 IPC（如 `tables:aggregate`）：按 X/Y 列与聚合方式在主进程完成分组统计，只返回聚合结果与采样预览行，不再整表过 IPC。
- [AC3.2] 分析页选表后：10 万行表从选中到图表/结论呈现 ≤ 1s（聚合由 SQL/主进程完成）；预览表最多渲染 1000 行（沿用 PREVIEW_MAX 约束）。
- [AC3.3] 同一会话内已加载的表元数据/聚合结果按 `updatedAt` 失效缓存，避免重复全量查询。
- [AC3.4] 新增 IPC 与 preload 契约在 `src/preload/index.ts` 与 `index.d.ts` 双文件同步，类型入 `src/shared/types.ts`。

### 需求 4：悬浮便利贴交互优化

**用户故事**
- 作为便利贴用户，我点击桌面悬浮图标，希望它流畅展开为大尺寸便利贴（现状已支持双态展开，本次保真并打磨动画与尺寸记忆）。
- 作为便利贴用户，我希望在便利贴上为某条便签关联一个程序/命令（如某 IDE、某网页、某脚本），展开后点一下即可直接打开对应程序，不用再去桌面找图标。
- 作为便利贴用户，我希望展开/收起、拖动、置顶、关闭等操作全程顺滑无跳变。

**验收标准（Must）**
- [AC4.1] 点击折叠图标展开为大尺寸便利贴：动画连贯（内容先就位、窗口再缩放的现有机制保持），展开/收起位置与尺寸记忆可靠，无最小尺寸顶回等回归。
- [AC4.2] 便签数据模型新增可选「打开程序」字段（`command`，类型入 shared/types.ts + stickies 存储），展开态便签卡片上有明确入口可编辑该字段。
- [AC4.3] 点击便签的「打开程序」按钮即执行关联命令：复用主进程 `command:run`（spawn detached），启动失败有明确错误提示；命令为空时按钮不出现。
- [AC4.4] 关闭悬浮窗保持现有确认行为；主窗口还原时自动收起逻辑不变。

## 四、边界与限制（逐项）

### 需求 1（分析增强）
- 数据源不变：粘贴 CSV / 导入文件（已 Worker 化）/ 选择数据整理表。不新增数据源类型。
- 图表类目上限沿用 Top-N 截断（capChartData），预览表上限 1000 行，导出明细受同类目上限约束并在报告中注明截断。
- 分析结论为**规则化统计描述**，不引入 LLM 依赖（本应用另有 AI 能力，但不作为本轮分析功能的依赖项）。
- 导出文件走现有 `exportText` / `exportBuffer` IPC，不新增文件写入路径。

### 需求 2（导入提速）
- 解析必须保持在 Web Worker（parseWorker/parseClient 现状），不得回移主线程；编码自动识别（utils/encoding.ts）保留。
- SQLite 已就绪（tablesCore：事务 + 200 行/批 INSERT + WAL），本轮不改存储引擎与表结构。
- 瓶颈判断（供架构师复核）：① create+update 两次 IPC 往返与两次落库；② 解析结果整表 JSON 结构化克隆跨进程；③ 导入完成后整表 setActive 的前端内存/渲染压力。优化对准这三点，不重写 tablesCore。
- 超大文件（百万行）不承诺秒级，承诺「有进度、不冻结、比现在快」。

### 需求 3（跨模块读取）
- `tables:get(id)` 惰性加载整表的行为对数据整理页保持不变；分析页改走新的聚合/采样通道，两者互不影响。
- 行存储为「每行一个 JSON 文本」，主进程聚合可用 SQL（json_extract）或全量取回主进程内存后归并，由架构师定夺；P0 只约束「聚合结果 + 采样行返回，不整表过 IPC」。
- preload 双文件（index.ts / index.d.ts）手写同步为硬约束，新增 API 必须双侧同步，类型入 shared/types.ts。
- 缓存失效以 `updatedAt` 为准；数据整理页内编辑（updateCell 已毫秒级）后返回分析页需取到新数据。

### 需求 4（便利贴）
- 已核实：折叠/展开双态、尺寸动画、位置记忆、关闭确认、还原主窗口自动收起均已存在（stickyPanel.ts / StickyPanelWindow.tsx），本轮以**保真回归 + 按需求补齐**为主，不推翻现有实现。
- 已核实：「打开对应程序」可复用主进程 `command:run` IPC（spawn, shell:true, detached）。安全边界：仅执行用户在便签中显式填写的命令，不提供任意命令输入框给外部来源。
- StickyNote 模型（stickies.json）需新增可选字段，旧数据无该字段时默认隐藏按钮，向后兼容，不做破坏性迁移。
- 单贴只读悬浮窗（stickyWindows.ts）与本悬浮面板（stickyPanel.ts）互不干扰，本轮不改前者。

## 五、待确认问题（架构师 / 主理人）

1. **分析结论是否需要 LLM 参与？** P0 按规则化统计结论实现（零依赖、离线可用）；若主理人希望接入现有 AI 能力生成「解读式」结论，请明确，P1 预留接口。
2. **主进程聚合实现路线**：用 SQLite `json_extract` 逐行聚合，还是主进程整表取回内存归并？前者省传输但每行 JSON 解析有成本，后者内存开销大。请架构师按典型数据规模（≤ 20 万行 × ≤ 30 列）定夺。
3. **导入单次 IPC 的载荷上限**：解析结果整表一次性传主进程（结构化克隆）在超大表下的内存峰值是否可接受？是否需要分批传输？请架构师评估。
4. **便签关联程序的字段形态**：单一 command 字符串即可，还是需要「名称 + 图标 + 命令」结构化字段？建议 P0 用单 command + 自动截取可执行文件名做展示。
5. **「点击悬浮便利贴展开为大尺寸便利贴」的现状确认**：主进程面板已支持点击展开；请主理人确认用户反馈是否主要针对单贴悬浮窗（stickyWindows）或交互细节问题，以便 P0 范围收敛在动画/尺寸记忆打磨 + 新增打开程序闭环。
6. **导出报告的默认目录**：跟随系统「另存为」对话框（现状 exportText 行为）还是固定工作目录？建议维持另存为。
